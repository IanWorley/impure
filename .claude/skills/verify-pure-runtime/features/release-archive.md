# Release archive

Players get the runtime as a release archive, not a checkout: `pure-runtime-<version>-<platform>.tar.gz` (`.zip` on Windows), assembled by `tools/package-release.sh` and published by `.github/workflows/release.yml` when a tag is pushed. Unpacked, it holds `pure-runtime` (built with `--features audio` and an rpath to `lib/`), the bundled LGPL FFmpeg (`libavcodec`, `libavutil`) in `lib/` (beside the executable on Windows), `sdk/` (`bin/XenonAnalyse`, `bin/XenonRecomp`, `XenonUtils/`, the third-party sources in `thirdparty/`, the glue and title fixes in `cpp/`, and `recomp/*.toml`), and `README.txt`, `LICENSE`, `THIRD_PARTY_NOTICES.md` and `licenses/`. The runtime's builder (`runtime/src/builder/mod.rs`) builds the game library from `PURE_SDK_DIR`, or `sdk/` beside the executable, and falls back to the source tree (`XENON_RECOMP_DIR` or `local/tools/XenonRecomp`, and `runtime/cpp`) only when neither exists. A broken rpath, a missing SDK file or a stale `sdk/cpp` would otherwise show up only for players.

## Sub-features

- `release-package` `tools/package-release.sh` produces the archive with the layout above, and its own guard passes on real input: no `.xex`, `.iso` or generated-code names in the staged tree, and no `__imp__sub_` or `pure_guest_load` symbols in the runtime; a planted game file makes it fail.
- `release-tag` `tools/release-tag.sh` accepts `vX.Y.Z` (full release) and `vX.Y.Z-rc.N`/`-beta.N`/`-alpha.N` (pre-release) matching `runtime/Cargo.toml`'s version, and refuses anything else; the release workflows pass actionlint.
- `release-sdk` from an unpacked archive outside any checkout, `pure-runtime <default.xex or disc image> --build-game` builds the library with `sdk/` alone: every tool it runs and every include it passes is under the archive's `sdk/`.
- `release-ffmpeg` the packaged runtime loads the bundled FFmpeg from `lib/` (`@executable_path/lib` on macOS, `$ORIGIN/lib` on Linux), fails to start without it, and plays sound with it (`audio: playing through the default output device at 48000 Hz`, `xma: … passes decoded … frames`).
- `release-readme` `README.txt` matches the app: the button labels, the key bindings, the data directories, the compiler commands, the build time and the disk-space figure.

## How to get to it (user POV)

- A player downloads the archive for their platform from the GitHub release (`gh release download <tag> --repo IanWorley/impure --pattern 'pure-runtime-*-macos-arm64.tar.gz'`), unpacks it, and follows `README.txt`: start `pure-runtime`, click **Open Pure disc image or default.xex...**, wait for the build, then **Play**.
- A maintainer pushes a tag (`release.yml` → `build-release.yml` → `tools/package-release.sh` on six runners), or builds one archive locally with `tools/package-release.sh <version> <platform> <output directory>`. Deleting the tag retracts the release (`retract-release.yml`).

## Driving it with the shell

Preconditions:

- `scripts/doctor.sh` passes its game, XenonRecomp and Clang checks (the runtime-binary check is about a source build; point `PURE_RUNTIME_BINARY` at the packaged binary once it exists). XenonRecomp must be a Release build made with the Ninja or Makefile generator (`grep -E 'CMAKE_BUILD_TYPE|CMAKE_GENERATOR:' local/tools/XenonRecomp/build-release/CMakeCache.txt`), since the script copies `build-release/<tool>/<tool>`.
- `FFMPEG_PREFIX` names an install from `tools/build-ffmpeg.sh`, not a system FFmpeg: `tools/build-ffmpeg.sh local/tools/ffmpeg/prefix local/tools/ffmpeg/work && export FFMPEG_PREFIX="$PWD/local/tools/ffmpeg/prefix"` (downloads the pinned 12 MB source; 44 seconds on an Apple M4, ending `FFmpeg 9.0.1 (LGPL) installed in …`).
- `cargo-about` (`cargo install cargo-about`), and 7-Zip on Windows.
- Disk: packaging builds into its own `runtime/target/package` (about 1.4 GB) and stages about 82 MB beside a 25 MB archive. A cold library build from `default.xex` adds 635 MB to the data directory (translation, objects and library); from the disc image, add the disc's 4.4 GB of files. The README's 15 GB is a safe margin; with less free, build from `default.xex`.
- `run=local/verification/$(date -u +%Y%m%dT%H%M%SZ)-release-archive; mkdir -p "$run"`, and the platform name from `build-release.yml`'s matrix (`macos-arm64`, `linux-x86_64`, …). The examples below use `macos-arm64` and the version in `runtime/Cargo.toml`.

- **Package.** `tools/package-release.sh 0.1.0 macos-arm64 dist > "$run/package.txt" 2>&1; echo "exit $?"`: exit `0`, last line `…/dist/pure-runtime-0.1.0-macos-arm64.tar.gz`. About 6 minutes cold on an M4 (`dist/` is ignored by Git).
- **Layout.** `tar -tzf dist/pure-runtime-0.1.0-macos-arm64.tar.gz | awk -F/ '{print $2"/"$3}' | sort -u` lists `LICENSE`, `README.txt`, `THIRD_PARTY_NOTICES.md`, `lib/libavcodec.63.dylib`, `lib/libavutil.61.dylib`, seven files under `licenses/` (FFmpeg, Fira Mono, SIMDe, XenonRecomp, libmspack, tiny-AES-c, `rust-crates.html`), `pure-runtime`, and `sdk/` with `XenonUtils`, `bin`, `cpp`, `recomp` and `thirdparty` (606 entries for 0.1.0).
- **The guard looked at something.** The script skips its symbol check without a word when `nm` fails, so check it read real symbols: `nm dist/pure-runtime-0.1.0-macos-arm64/pure-runtime | wc -l` is in the hundreds of thousands (258,148), and `… | grep -cE '__imp__sub_|pure_guest_load'` prints `0`. `tar -tzf dist/….tar.gz | grep -iE '\.xex$|\.iso$|ppc_recomp|ppc_func_mapping|ppc_config\.h'` prints nothing.
- **The SDK is current.** `diff -r runtime/cpp dist/pure-runtime-0.1.0-macos-arm64/sdk/cpp && diff -r recomp dist/pure-runtime-0.1.0-macos-arm64/sdk/recomp` prints nothing.
- **The guard refuses.** In a throwaway clone, plant an empty game-named file where the script copies from: `probe=$(mktemp -d /tmp/release-guard-probe.XXXXXX); git clone -q . "$probe"; touch "$probe/runtime/cpp/probe.xex"` (an APFS clone of the target directory saves a full rebuild: `mkdir -p "$probe/runtime/target"; cp -Rc runtime/target/package "$probe/runtime/target/"`). `(cd "$probe" && XENON_RECOMP_DIR="$OLDPWD/local/tools/XenonRecomp" tools/package-release.sh 0.1.0 probe dist); echo "exit $?"` ends `error: game content in the release: …/dist/pure-runtime-0.1.0-probe/sdk/cpp/probe.xex`, exit `1`, and `ls "$probe/dist"` shows only the staging directory, no archive. Then `rm -rf "$probe"`. The symbol half of the guard has no such probe: it would need a runtime linked with game code, which no build makes any more.
- **Tags.** `for t in v0.1.0 v0.1.0-rc.1 v0.2.0 v0.1 v0.1.0-rc; do tools/release-tag.sh "$t"; echo "exit $?"; done`: `prerelease=false` and `prerelease=true` with exit `0`, then `error: v0.2.0 does not match runtime/Cargo.toml's version 0.1.0; bump it first` and `error: … is not a release tag: …` twice, each exit `1`. `actionlint .github/workflows/{build-release,release,retract-release}.yml` and `shellcheck tools/package-release.sh tools/build-ffmpeg.sh tools/release-tag.sh` print nothing.
- **Unpack outside the checkout.** `x=$(mktemp -d /tmp/pure-release.XXXXXX); tar -xzf dist/pure-runtime-0.1.0-macos-arm64.tar.gz -C "$x"; archive="$x/pure-runtime-0.1.0-macos-arm64"; xex="$(cd originals/disc && pwd -P)/default.xex"`. Everything below runs from `"$archive"` (`git -C "$archive" rev-parse` fails: no checkout in reach).
- **FFmpeg linkage.** `otool -l "$archive/pure-runtime" | grep -A2 LC_RPATH` shows the one rpath `@executable_path/lib`; `otool -L` shows `@rpath/libavcodec.63.dylib` and `@rpath/libavutil.61.dylib`, and `otool -L "$archive/lib/libavcodec.63.dylib"` the same `@rpath/libavutil.61.dylib`. `(cd "$archive" && DYLD_PRINT_LIBRARIES=1 ./pure-runtime --bogus 2>&1 | grep -E 'avcodec|avutil')` shows both loaded from `$archive/lib/`, then the usage line and exit `2`. On Linux: `readelf -d pure-runtime | grep RPATH` shows `$ORIGIN/lib` (an `RPATH`, not `RUNPATH`) and `LD_DEBUG=libs ./pure-runtime --bogus` the loads. Control: in an APFS clone without `lib/` (`c=$(mktemp -d); cp -Rc "$archive" "$c/"; rm -rf "$c"/*/lib`), `(cd "$c"/pure-runtime-* && ./pure-runtime --bogus)` exits `134` with `dyld[…]: Library not loaded: @rpath/libavcodec.63.dylib`, having tried only that copy's `lib/` (never a Homebrew FFmpeg of the same version).
- **Builds from `sdk/` alone.** In a scratch data directory, with `XENON_RECOMP_DIR` pointed nowhere so the fallback could not work, and the runtime's child processes sampled once a second:

  ```sh
  data=$(mktemp -d /tmp/pure-release-data.XXXXXX); raw=$(mktemp)
  (cd "$archive" && exec env -u PURE_SDK_DIR PURE_DATA_DIR="$data" XENON_RECOMP_DIR=/nonexistent/XenonRecomp \
      ./pure-runtime "$xex" --build-game) > "$run/sdk-build.txt" 2>&1 &
  build=$!   # exec: the subshell becomes the runtime, so its tools are this PID's children
  while kill -0 "$build" 2>/dev/null; do ps -axww -o ppid=,command= | awk -v p="$build" '$1 == p { $1 = ""; print }' >> "$raw"; sleep 1; done
  tr ' ' '\n' < "$raw" | grep '^/' | sed -E 's#^(.*/sdk/(bin/[^/]+|[^/]+)).*#\1#; s#^(.*/local/tools/[^/]+).*#\1#; s#^(.*/runtime/cpp).*#\1#; s#^(.*/games/)[^/]+/.*#\1<SHA-256>/…#' \
      | sort | uniq -c | sort -rn > "$run/sdk-children.txt"; rm -f "$raw"
  ```

  `sdk-build.txt` shows the stages of [game-library.md](./game-library.md) and ends `The game library is ready: …/pure_game.dylib`, exit `0` (584 seconds on an M4 while other builds shared it; about 10 minutes alone). `sdk-children.txt` counts `$archive/sdk/thirdparty`, `sdk/XenonUtils`, `sdk/cpp`, `sdk/bin/XenonAnalyse` and `sdk/bin/XenonRecomp`, the Command Line Tools' `clang++` and `MacOSX.sdk`, the data directory's `games/<SHA-256>/…` and the `default.xex`, and nothing under `local/tools` or `runtime/cpp`. Run again, it prints only `Checking your copy of the game` and ready (0.11 seconds), and `nm -gU "$data"/games/*/pure_game.dylib | grep -c ' _pure'` prints `11`. The summary keeps only directories, never generated file names.
- **The archive's SDK is the one resolved.** In an APFS clone of `"$archive"` without `sdk/bin/XenonAnalyse`, `--build-game` prints `Checking your copy of the game`, then `<clone>/sdk/bin/XenonAnalyse is missing: this runtime's build tools are incomplete (see docs/tooling.md)`, exit `1`. In a clone without `sdk/` at all it names `/nonexistent/XenonRecomp/build-release/XenonAnalyse/XenonAnalyse` instead: the fallback exists (`strings pure-runtime` shows the packaging checkout's `runtime` path baked in), so only `sdk/` kept the main build off it. Both leave the scratch data directory empty.
- **Audio from the bundled FFmpeg.** The game decodes XMA only once Return takes it past its start-up screens, so borrow the tutorial script's first presses: `s=$(mktemp /tmp/pure-title.XXXXXX); { grep -E '^[0-9]+ (down|up) Enter$' .claude/skills/verify-pure-runtime/inputs/to-tutorial.txt | awk '$1 <= 1986'; echo '3600 exit'; } > "$s"`, then `PURE_DATA_DIR="$data" PURE_RUNTIME_BINARY="$archive/pure-runtime" VERIFY_RUN_SECONDS=90 .claude/skills/verify-pure-runtime/scripts/run.sh release-audio "$xex" --input-script "$s"; rm "$s"`. `runtime.log` has `3 title fixes in place`, `entry point 0x82254d60`, `audio: first audio frame submitted`, `audio: playing through the default output device at 48000 Hz`, and about 30 seconds in `xma: 131 passes decoded 164 frames in the last 30s` (the same count as a source build at that point); the summary ends `frames presented: 3600`, `runtime exit: 0`. Without the presses, 60 seconds log `playing through …` but no `xma:` line. The run plays through the host's speakers; to judge the sound itself, add `PURE_AUDIO_CAPTURE` as in [audio.md](./audio.md).
- **Launcher.** `PURE_DATA_DIR=$(mktemp -d) PURE_RUNTIME_BINARY="$archive/pure-runtime" VERIFY_RUN_SECONDS=8 .claude/skills/verify-pure-runtime/scripts/run.sh release-launcher --choose`: `still running after 8s`, `window: present` (see [launcher.md](./launcher.md)).
- **README.** `cmp tools/release/README.txt "$archive/README.txt"` is silent, then compare each claim with the code that makes it true:
  - the labels: `grep -F "$(sed -n 's/^const OPEN_LABEL: &str = "\(.*\)";/\1/p' runtime/src/launcher.rs)" "$archive/README.txt"` matches, and so does `grep -F 'click Play'` (`PLAY_LABEL`);
  - the keys: the `Keyboard:` lines name the 21 entries of `BINDINGS` in `runtime/src/controller.rs` (W right trigger, S left trigger, A/D left stick, I/K and J/L right stick, Enter and Space A, Backspace B, X, Y, Q/E shoulders, Escape Start, Tab Back, arrows D-pad), and the controller's doc comment covers "a gamepad works too";
  - the data directories match `runtime/src/data_dir.rs` (on Linux, `$XDG_DATA_HOME/pure-runtime` when that is set);
  - the compiler commands match `install_hint()` in `runtime/src/builder/mod.rs`, and "about 10 to 15 minutes" matches the `Compiling the game` stage;
  - `pure-runtime <your.iso> --build-game` fits the usage line `./pure-runtime --bogus` prints;
  - "about 15 GB of free disk space" covers a measured cold build: `du -sh "$data"` after the build above (635 MB from `default.xex`), plus 4.4 GB of disc files from an image, is about 5 GB.
- **Proof then cleanup.** Keep the `.txt` files and run directories; `rm -rf "$x" "$data"` (the data directory holds the compiled game: game-derived, never evidence). `dist/` and `runtime/target/package` stay for the next run; remove them when the space is needed.

## Gotchas

- A release published on GitHub (`gh release list --repo IanWorley/impure`) can stand in for packaging locally; the `release-sdk`, `release-ffmpeg` and `release-readme` recipes are the same against its unpacked archive. Its runtime's baked fallback path is the CI runner's, which never exists on a player's machine.
- Packaging and every proof here are per platform: an archive built on macOS proves nothing about the Linux rpath or the Windows DLL search. The other platforms are built only by `build-release.yml` on its runners.
- Proven live so far on macOS arm64 only (Apple M4, 2026-10-14, commit `8731056`, a locally packaged 0.1.0): every recipe above, with the library built from `default.xex`. Not yet proven: the Linux and Windows archives; `--build-game` from the disc image through the archive (the disc copy is the same code [game-library.md](./game-library.md) proves from source); the symbol guard refusing; the workflows on GitHub (only actionlint); a published release (none exists yet); the button label as drawn on screen and the default data directories (source only, runs used a scratch `PURE_DATA_DIR`); and a downloaded archive under Gatekeeper, whose quarantine flag a local `tar` never sets, so whether the unsigned `sdk/bin` tools run once the README's right-click Open has let `pure-runtime` start is unknown.
- `tools/package-release.sh` rebuilds the runtime into `runtime/target/package` with an rpath to the bundled FFmpeg; do not point `PURE_RUNTIME_BINARY` at that binary in place: `target/package/release/` has no `lib/` beside it, so it exits `134` with `Library not loaded: @rpath/libavcodec.63.dylib`, and with no `sdk/` either it would prove nothing about the archive. Use the unpacked archive's.
- A Homebrew or system FFmpeg can have the same library versions as the bundled one; only the dyld/ld.so trace (or the no-`lib/` control) tells which was loaded.
- The SDK's missing-file error points players to `docs/tooling.md`, which the archive does not contain.
- Never push a tag to test `release.yml`: it publishes a release. Use a fork, or the recipes above.
