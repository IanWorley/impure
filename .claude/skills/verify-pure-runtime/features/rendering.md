# Rendering the game's frames

The window shows what the game draws. Each shader the game loads is translated from Xenos microcode to WGSL and checked with naga. Each draw then runs on the host GPU through wgpu, on the device Bevy created. An EDRAM surface is a host texture at sample resolution (2x2 samples per pixel for 4x multisampling, with depth and stencil surfaces alike), a resolve averages the samples of its rectangle into a host texture named by its destination address (a resolve to a row further down an existing destination, as the screen's lower tile is, writes into that texture; red and blue are exchanged when the resolve asks), and the swap packet VdSwap queues copies the presented front buffer into the window, ignoring alpha as the console's scan-out does. Draws sampling the top-left part of a resolve destination get a copy of that part. Draws and resolves are recorded into one command buffer per frame and submitted at the swap; consecutive draws to the same surfaces share a render pass, and indexed lists and strips use a host index buffer. A front buffer resolved with red and blue exchanged is exchanged back when shown, as the console's display reads it. On a software GPU (llvmpipe), 2x multisampled surfaces are drawn at one sample per pixel, halving their cost. A draw's pixels pass the alpha test and alpha to coverage `RB_COLORCONTROL` asks for (as a discard; host pixels are guest samples, so coverage is per sample, with the console's dither), and triangles are culled as `PA_SU_SC_MODE_CNTL` asks (rectangles never are). Shaders sample 2D textures and cube maps (six faces, 4 KiB apart in guest memory), applying fetch offsets and the level `setTextureLOD` sets (only base levels are uploaded, so that level clamps to it). EDRAM is plain memory, and the game relies on it: in the tutorial it draws the scene in two 2x tiles, resolves depth to an 8888 texture, and in its 1x pass draws that texture as colour where the depth surface lies to restore depth. Read as 8888, a depth resolve is the packed words EDRAM held (24 bits of 20e4 or unorm depth above 8 of stencil), and colour drawn over a depth surface becomes its depth before the next draw tests it, with the 40-sample halves of each 80-sample tile exchanged as EDRAM keeps depth (stencil is not carried). The other way round too: depth or stencil written where a colour surface shares the base (by a draw or a resolve's clear) becomes that colour before it is next drawn or resolved; the game clears its 320x180 light-shaft buffer that way, with a depth-only clear at 4x multisampling over the colour. Draws with clipping off (`PA_CL_CLIP_CNTL`) have their depth clamped rather than clipped, as Direct3D's clear rectangles sit a rounding error below zero. Pixel shaders get the pixel parameters (`ps_param_gen`: the pixel's position, back-facing in X's sign) in the register `SQ_CONTEXT_MISC` names; the sun glow tests its occlusion with them. Without these the light-shaft buffer kept the previous frame's image, which was blurred and added back each frame, and the whole tutorial washed out to a yellow-white haze. Textures are untiled and decoded on the CPU (8-, 16- and 32-bit formats, DXT1-5, and 32-bit and 4x16-bit float); formats with fewer than four components repeat their last one when sampled, as the console's do. Colour surfaces are 8-bit RGBA or 32-bit float; depth surfaces honour the 20e4 float format's clear values, and depth resolves copy each pixel's first depth sample into a float texture. The game's 2D screens appear this way: a black video frame (its Bink movies decode to black), then, as keys move it on, the safety warning, the ESRB rating, the autosave notice, the loading screen, the title screen (`Press START`), the save dialog, the tutorial's loading screen and then the tutorial itself (about 1,600 to 2,400 draws a frame): its instruction screens over the blurred track, the countdown and the `Complete a lap` objective.

Not reproduced yet, each reported once in the log as `WARN renderer: not reproduced: …`:

- render target formats other than 8-bit RGBA and 32-bit float (`render target format N`), and resolves to them (`resolves to format N`);
- blending into render targets the host cannot blend (`blending into Rgba32Float render targets`), and blend controls with no host equivalent (`blend control 0x…`);
- texture formats the decoder lacks (`texture format N`), textures past the end of physical memory, primitive types with no host equivalent (`primitive type 0x…`), and draws reading more guest memory than a batch holds;
- a GPU error in a recorded pass (`… failed: <error>`).

Resolved textures are never written back to guest memory, so a title reading them with the CPU would not see them; that is not logged.

Shaders that translate with something skipped are reported once each as `shader: … valid WGSL, not translated: {…}` (see `boot-shader-translation`); none do in the tutorial or a race.

Two failures used to end tutorial runs, and are what a long run now checks for. Command memory overwritten by a second thread showed up as `gpu: stalled for 2000 polls` or `gpu: a packet wrote … to CP_RB_WPTR`: every guest thread had thread ID 0, so loader threads passed Direct3D's device-owner check and wrote into the command buffer alongside the main thread (fixed in `guest.rs`). After a few hundred gameplay frames, frames stopped with no message: the game's job system lost an activation or a wakeup to host preemption, and its main thread waited for a job forever (fixed by the overrides in `runtime/cpp/patches.cpp`).

## Sub-features

- `rendering-shaders` translates every loaded shader to valid WGSL (see `boot-shader-translation` in [boot.md](./boot.md)).
- `rendering-present` presents guest frames: `renderer: first guest frame presented from physical 0x01220000`.
- `rendering-screens` shows the start-up screens in the window as the game reaches them.
- `rendering-gaps` reports each unreproduced feature once.

## How to get to it (user POV)

- Run the game and press Return (A) a few times once the window has been black for about 15 seconds.

## Driving it with run.sh

Preconditions:

- `scripts/doctor.sh` prints `ready`; `xdotool` and ImageMagick (`import`, `convert`) are installed. Set `PURE_DATA_DIR` to a fresh directory under `local/verification/`, since moving on through the screens reaches the save code (see [saves.md](./saves.md)).

- **Unit coverage.** `cargo test renderer` and `cargo test translate` in `runtime/` (two runs: cargo takes one filter) check the constants layout against the WGSL struct (with naga's layouter), the viewport and pixel-centre transform, primitive expansion and blend mapping, and that synthetic shaders translate to valid WGSL.
- **First frame.** Run 25 seconds: `runtime.log` has `renderer: rendering guest draws with wgpu` and `renderer: first guest frame presented from physical 0x01220000`, with no `ERROR bevy_render` line. `screenshot.png` is opaque black (`convert screenshot.png -format %c histogram:info:-` shows one near-black colour, not `#0D0D14`): the game's intro video frame is black (its Y plane is 16 throughout; `VERIFY_RUST_LOG=info,renderer=debug` logs each texture's mean byte).
- **Screens.** Start a 75-second run in the background and, once its `summary.txt` shows the display, wait 15 seconds, focus the window (see [input.md](./input.md)) and, 3 seconds apart, take a screenshot of that display with `DISPLAY=:1NN import -window root shot-<n>.png` before pressing Return ×4, Down, Return ×2, Escape, Return ×3. The screenshots after the first two presses show the safety warning, then the ESRB rating, then the autosave notice: hundreds of colours each (`convert shot-<n>.png -format '%k colors' info:`). Look at them locally; they are the game's own images, so never quote or commit them.
- **Title screen.** Drive a 180-second run the same way, pressing Return ×4, Down, Return ×2, Escape and then Return ×9. Around the twelfth screenshot the loading screen (tens of thousands of colours) and then the title screen appear; `cargo test texture` covers the tiling and DXT decoding.
- **Tutorial loading screen.** Drive a 330-second run pressing Return ×14, Escape (Start, at the title screen), then Return about every 3 seconds. From about the 37th screenshot the tutorial's loading screen shows (over 100,000 colours). `cargo test edram` covers the sample layout, window offsets and resolve rectangles.
- **Tutorial 3D.** Drive the same keys for 600 seconds with `VERIFY_RUST_LOG=info,video=debug`. Within a few minutes `video: frame N presented (1280x720, D draws)` lines show D around 1,600 to 2,400, and a screenshot of the display shows the tutorial: an instruction screen over the blurred track, or the countdown and `Complete a lap` over the rendered world. The load only finishes since worker threads see the hardware thread their affinity names (the level loader keeps per-processor state).
- **Tutorial gameplay without a hang.** Drive the same keys for 4,800 seconds or more. Frames keep coming (find the first gameplay frame with `grep presented runtime.log | awk -F'[(,]' '{split($3,a," "); if (a[1]+0>500) {print; exit}}'`), and `grep -E "gpu: stalled|a packet wrote|panicked|guest stopped|host crash" runtime.log` prints nothing. Before the fixes above, presents stopped 450 to 650 gameplay frames in; a 7,200-second run now passes about 1,080 with none of those lines.
- **Countdown and depth.** Add captures every 15 frames from 2,700 to 2,900 to the tutorial script: on an M4 the countdown's 3, 2, 1 and `Go!` appear around frames 2,760, 2,775, 2,790 and 2,820. The rider is solid, with the trees, smoke and banner behind him and no grass or distant trees drawn over him, and the foliage has no rectangular holes. A `resolves` dump of a riding frame shows why: the depth resolve after the 1x pass (the second `-02080000` image) matches the tiled pass's (`-02300000`) through the rider and ground. The same dump logs each draw (shaders, target, blend, `RB_COLORCONTROL`, depth, culling, primitive, program control, colour mask, viewport mode, scissor, surface and depth info, textures, and the pixel constants of full-screen passes) and resolve (with its colour source) under `dump`, for matching passes to shaders (shader disassembly is under `VERIFY_RUST_LOG=info,shader=trace`).
- **Against Xenia.** Xenia's compatibility reports for Pure (title 425607D9: [xenia-project/game-compatibility#1592](https://github.com/xenia-project/game-compatibility/issues/1592), [xenia-canary/game-compatibility#836](https://github.com/xenia-canary/game-compatibility/issues/836)) have tutorial screenshots: a blue sky, dark trees, contrasty brown dirt and a sharp rider. The ride captures should look the same; a yellow-white haze over everything, or sun glow in front of trees and terrain, means the light-shaft pass has gone wrong (check that the clears of the 320x180 surface at EDRAM `0x3a0` land: its `resolves` image after the clears is black where no sun shows).
- **Gaps.** `grep 'not reproduced\|not translated' runtime.log` lists each missing feature once; after a tutorial or race run it is empty, and the last `frames presented` line's three shader counts are equal.
- **macOS (Metal), or any host without `xdotool`.** Drive [`inputs/to-tutorial.txt`](../inputs/to-tutorial.txt) for 400 seconds with a release build: `PURE_RUNTIME_BINARY=$PWD/runtime/target/release/pure-runtime VERIFY_RUN_SECONDS=400 .claude/skills/verify-pure-runtime/scripts/run.sh tutorial originals/disc/default.xex --input-script .claude/skills/verify-pure-runtime/inputs/to-tutorial.txt`. The frame captures (`shot-NNN.png`) show the same screens as above; on an Apple M4 the warning is `shot-000`, the rating `shot-001`, the autosave notice `shot-003`, a 3D loading scene `shot-004`, the title screen `shot-005`, then (with no save) `No Save File Found` and `Save Successful`, the tutorial's loading screen by `shot-008`, and by about frame 3,000 to 3,600 the tutorial's 3D world (1,600 to 2,500 draws a frame): then the lap itself (`ride-NNNN.png`): the rider on the ATV from behind, the track, rocks, the PURE truck with spectators; `Complete a lap` gets its green star and `Preload` appears. Long spikes or huge flat triangles across the view mean strips are being drawn through their reset index (see `host_indices` in renderer.rs). The exit at frame 9,150 ends the run with `runtime exit: 0`. With `VERIFY_RUST_LOG=info,video=debug`, count `video: frame N presented` lines per second for the frame rate: on an M4 release build about 19 during the instructions and 25 to 27 riding.

## Gotchas

- On a real GPU the command processor thread (one core walking packets and recording draws) limits the frame rate, not the GPU. Profile it with macOS's `sample <pid> 5` and look at the `command-processor` thread; the guest's main thread mostly spins in Direct3D's wait for the GPU.
- A hang shows as frames stopping with no stall line. The tutorial's level load presents nothing for 15 to 20 seconds, so wait at least 40 seconds before calling it one; then sample the process (`sample <pid> 5` on macOS) and read the `wait:` lines. That is how the macOS hangs were traced to the job system (the main thread waiting on a semaphore only one job thread ever released), and then to `patches.cpp` not being linked at all: check for `title fixes in place` near the top of `runtime.log`.
- The tutorial's fly-over and instructions last a fixed time, so the frame they end on depends on the frame rate; a script keyed on frames must keep tapping A (and hold the throttle) across that range rather than press once.
- Under Xvfb the GPU is llvmpipe, a CPU rasterizer. The translated shaders are heavy for it, so in the tutorial a frame takes about 4 to 5 seconds there (each swap waits for the previous frame's GPU work). Frame-rate claims belong to the boot recipe's pre-rendering phase or to real GPUs. Runs started at the same time share the CPU and slow each other down.
- A frame that comes out as the window's clear colour `#0D0D14` means the display sprite is transparent or missing, not that the game drew that colour.
- Screenshots and `shader=trace` output are derived from the game. Keep them in `local/verification/`.
